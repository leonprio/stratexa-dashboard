# Nota de Versión v9.4.4 - Blindaje de Integridad de Identidades

## Información de la Versión
- **Versión anterior:** 9.4.3
- **Nueva versión:** 9.4.4
- **Etiqueta de Versión (VERSION_LABEL):** `v9.4.4-USER-IDENTITY-INTEGRITY-HARDENING`
- **Estado de despliegue de Reglas:** `LOCAL_ONLY_NOT_AUTHORIZED_FOR_DEPLOY` (Requiere auditoría separada multiaplicación antes del deploy).

## Resumen de Cambios
Esta versión menor (v9.4.4) implementa un blindaje de seguridad exhaustivo en el flujo de identidades de la plataforma Stratexa Dashboard. Las modificaciones aseguran que no exista desalineación o cruce de datos entre Firebase Authentication y Cloud Firestore.

### 1. Utilidad de Integridad (`utils/userIdentityIntegrity.ts`)
- Se introduce una utilidad de validación pura, determinista y tipada que centraliza las reglas de coincidencia de UID.
- Valida la coincidencia exacta de `documentId`, `profile.id` y `authUid`.
- Detecta perfiles históricos desalineados y lanza advertencias específicas.
- Permite administradores legítimos con campo `dashboardAccess` vacío sin clasificarlo como error de autenticación.

### 2. Flujo del Servicio Firebase (`services/firebaseService.ts`)
- Se añade el método `deleteAuthUserDirectly` para habilitar compensación best-effort si la escritura de perfil en Firestore falla tras crear la credencial en Auth.
- La creación de la cuenta secundaria Auth ahora expone el objeto temporal `userInstance` para permitir su remoción en caso de falla.

### 3. Componente Administrador (`components/UserManager.tsx`)
- Se implementa una máquina de estados para la creación de usuarios que incluye: `VALIDATING_INPUT` -> `CHECKING_HISTORICAL_PROFILE` -> `CREATING_AUTH` -> `CREATING_PROFILE` -> `VALIDATING_READBACK` -> `SUCCESS`.
- En caso de falla en `CREATING_PROFILE` o `VALIDATING_READBACK`, se invoca la compensación. Si esta falla, se reporta `RECOVERY_REQUIRED`.
- Se reestructura el flujo de borrado sustituyéndolo semánticamente por **"Desvincular del Tablero"** ya que desde el cliente solo se elimina el perfil en `tbl_users` y la credencial de Auth permanece en el servidor. El diálogo de confirmación advierte explícitamente sobre esta limitación.

### 4. Flujo de Login (`App.tsx`)
- Las credenciales de autenticación válidas que no posean perfil en `tbl_users` producen un bloqueo controlado con el error structured `PERFIL_TABLERO_NO_VINCULADO`.
- Los perfiles desalineados devuelven `PERFIL_TABLERO_DESALINEADO`.
- Se elimina la cuenta de prueba `admin-backup` del código fuente de bypasses y del validador de reglas de base de datos local para cumplir con el principio de mínimo privilegio.

### 5. Reglas de Firestore (`firestore.rules`)
- Se eliminan las cuentas bypass y de prueba de las reglas locales.
- Se mantiene la guardia `isTableroUser` requiriendo autenticación y la existencia del perfil en `tbl_users/{uid}`.
- > [!IMPORTANT]
  > Las reglas locales están marcadas como exclusivas para auditoría multiaplicación separada. El despliegue de estas reglas junto con el código frontend queda estrictamente bloqueado.
